#+TITLE: portia lore

* portia is a harness, not a porter
The spec describes a tool that *drives MODEL* to do the porting; portia
itself does no porting. So the deliverable is a deterministic CLI - it
owns the command, the target directory, the prompt, and the
post-condition - plus the prompts MODEL is handed. This mirrors sclr:
the harness is deterministic, inference is not. (Confirmed by the user
in collab: the spec is a description of the tool to build, prompts
included, not a task for me to perform by hand.)

* the model is stubbed for tests
portia's own logic - argument handling, prompt assembly, the
port-shape check - is deterministic and tested with a stubbed MODEL,
exactly as sclr does. No ports tree is needed to develop or test it.

* a port is named by an origin or a path, resolved before MODEL
Every command takes one argument naming the port, in one of two forms:
- an origin =category/port= (one slash), taken relative to =PORTSDIR=;
  the ports tree is =PORTSDIR=.
- a path =.../category/port= (more than one slash) to a port dir inside
  a tree; the origin is its last two components and the tree is the
  path above them.
An argument with no =category/port= tail is neither form and is a hard
error.

Trailing slashes are stripped before the form is decided: a shell's tab
completion appends one to a directory, and the path form splits on
slashes, so an unstripped trailing slash reads the empty tail as a
component. Every part then shifts up - the tree is taken one level too
deep and the origin comes out malformed. Stripping first makes
=.../devel/lua-lunitx/= resolve exactly as =.../devel/lua-lunitx=.

portia resolves this itself, deterministically, *before* calling MODEL
(confirmed by the user in collab). The alternative - handing the raw
argument to the model to interpret - was rejected because the harness
owns the concrete port directory: it verifies the port's shape and
commits the result, both of which need that directory known up front. A
model that only reports the directory back afterwards would push the
shape check and the commit past the point portia can guarantee them.

Resolution yields three values - the origin (told to the model and
committed), the ports tree, and the port directory (=tree/origin=,
created before the model runs). Unifying both forms to the same three
values is the point: everything downstream works the same whichever way
the port was named.

* the ports tree locates version control; for an origin it is PORTSDIR
A port lands at =tree/category/port=, mirroring a real ports tree. For
an origin the tree is =PORTSDIR=, defaulting to =.= so the tool works
from inside a checkout without configuration; for a path the tree is
embedded in the argument, so =PORTSDIR= is not consulted. portia
creates the port directory before invoking MODEL so the model has a
known place to write.

* MODEL matches sclr's contract
=MODEL= (default =claude=) is left unquoted at the call site so extra
words split into flags, letting tests substitute a stub and real use
add a permission mode. Same rationale as sclr.

* prompts are files portia reads, one per command
Each command has a prompt under =prompts/=. Keeping them as files (not
inline heredocs) mirrors sclr feeding =agent.org= to the model, and
lets the prompts - the real porting knowledge - evolve without touching
the harness.

* =new= creates the whole port; there is no separate bootstrap
An earlier design split creation in two: =new= laid down a skeleton
(=Makefile=, =pkg-descr=) and a separate =bootstrap= fetched the
distfile, derived the build system, and produced =distinfo=. The split
bought =new= a fixed, distfile-independent post-condition, but the user
judged that not worth a mandatory two-step dance: =new= should research
the distfile and produce a complete port in one pass (confirmed in
collab). So there is one creation command. Its post-condition is a
complete port, =distinfo= included, which does assume a fetchable
distfile - a port with nothing fetchable yet, pre-release or private,
is out of scope by that choice, the price of the simpler surface.

* portia does not build; verification is static analysis
The spec constrains portia - the harness and the model both - never to
build the port. Verification is static analysis only: fetch the
distfile, extract it, read the sources, derive =distinfo= from what was
fetched. The real build is checked out of band by an operator, so a bad
guess surfaces there rather than in a model turn, which cannot be
trusted to judge a build anyway.

The harness never built - it stubs the model and checks the port's file
shape - so this constraint lands in the prompts, like the
changelog-reference requirement. =new= and =update= fetch and extract
the distfile to inspect it and to derive =distinfo=, but do not run
=make=, =configure=, or a compiler.

* use the framework; do not invent - a prompt constraint
The spec forbids inventing creative solutions: a language ecosystem
almost always has dedicated make targets and =USES= knobs for the
mechanical parts - dependencies especially (=make cargo-crates=, =make
gomod-vendor=, the Python and PHP helpers) - and any non-obvious problem
has been solved in the ports tree before. So the prompts tell the model
to reach for that machinery and to follow an existing port rather than
hand-roll a rule.

Like the no-build constraint, this shapes the model's approach, not the
harness's behavior, so it lives in the prompts, not the code, and adds
no man-page contract: portia checks the same files and commits the same
way however the port was produced. The sharp edge is the spec's own
stance - better to fail than to ship a bespoke solution the community
will reject - which the prompts state outright so the model stops rather
than improvises when the framework path is unclear. Both =new= and
=update= carry it, since both do real dependency work.

* the framework's *current standard*, not merely *a* framework path
"Use the framework; do not invent" is necessary but not sufficient: an
ecosystem often ships several mechanisms for one task, and a once-standard
one the tree has moved away from is as wrong as an invented solution -
it *is* the framework, just the deprecated part of it. A confirmed
failure taught this concretely: a Go port was carried on =GH_TUPLE=
vendoring while 511 of 512 module-based Go ports had moved to
=GO_MODULE=; the lone outlier was unbuildable, and "use the framework"
did not catch it because =GH_TUPLE= is framework machinery. So the
=new= and =update= prompts now tell the model to pick the mechanism
comparable ports use *now*, measured by prevalence, and to treat a
mechanism only a handful of ports still use as a warning sign, not a
template. The rule is stated generally; the model derives the specific
(for Go it lands on =GO_MODULE=).

Two more lessons from the same failure, also prompt-only:
- *Understand what the build consumes.* A dependency generator exiting 0
  is not evidence the config is complete: the Go build reads
  =vendor/modules.txt=, which =GH_TUPLE= never produces, so every
  vendored package was ignored. The prompts now require the model to
  know which artifacts the build reads, confirm the config produces a
  complete and consistent set, and verify the fetched upstream actually
  provides what the mechanism assumes (does it vendor? ship a lockfile?).
  Static analysis being the *only* verification portia has is the reason
  this matters, so the prompts frame it that way: since you cannot build,
  mechanistic understanding is the only net against build-breaking config.
- *=update= must not treat the port's existing scheme as given.* A bump
  inherits whatever mechanism the port already uses, so mechanically
  re-running its generator reproduces a pre-existing defect - exactly how
  the failure arose. =update.org= now tells the model to sanity-check
  that the existing mechanism is still standard and still sound before
  bumping it.

These stay in the prompts for the same reason "use the framework" does:
they shape the model's approach and add no harness contract. Both =new=
and =update= carry them, since both do real dependency work.

* consensus is the default; a working minority scheme does not justify itself
The =current standard= rule has an inverse failure mode. Told to prefer
the mechanism the tree uses now, the model migrates to it, hits an
obstacle, and retreats to the minority scheme - now self-justified by
"it works". A confirmed =zk= update did exactly this: it migrated
=GH_TUPLE= to =GO_MODULE=, found the =GO_MODULE= fetch 404s because an
upstream test-fixture filename holds a character invalid in a Go module
path, and kept =GH_TUPLE= because it still fetches. That retreat is the
very error the =current standard= rule exists to prevent, reached from
the other side.

The framework prizes consistency, so consensus is the strong default and
a minority scheme is a last resort, not a first workaround. An obstacle
the standard mechanism hits is a problem to solve, not a verdict: the
spec's premise is that any problem has been solved in the tree before,
so the model must research how other ports *on the standard mechanism*
handle that same obstacle before concluding the standard cannot be used,
and fall back only once it has confirmed no standard remedy exists -
recording why. "It works" is necessary, not sufficient: that a
nonstandard scheme fetches and generates cleanly is no reason to prefer
it. The =understand what the build consumes= check guards against a
config that generates cleanly yet cannot build; it is not an escape
hatch back to the minority scheme, which is exactly how it was misused
here.

Prompt-only, like the rest of the mechanism guidance: =new= and =update=
both carry it, since both do real dependency work. The harness keeps no
contract about which mechanism a port uses.

* the post-condition is the port's shape
The spec's second goal is checking MODEL's output. portia's check is
that the expected port files exist and are non-empty in the port dir.
Both commands produce a complete port - =Makefile=, =distinfo=,
=pkg-descr=. =new= fetches the distfile to derive =distinfo=; =update=
regenerates it for the bumped version.

* portia commits the port, the model writes the message
The spec's third goal is committing at natural stopping points,
following FreeBSD conventions, with changelog references. The commit is
split the same way as everything else in portia: the harness owns the
deterministic edge (=git add= + =git commit=), the model owns the
judgement (the message - subject convention, body, and the changelog
links the spec asks for). The message is carried on a scratch file
whose path the prompt hands the model, then read back and committed
with =-m=.

The scratch file lives *inside the port directory*, not in =/tmp=. The
model's file access is scoped to the tree it works in - the same scope a
permission mode like =acceptEdits= grants - so a path outside that tree
is one the model reports writing but cannot actually write. An earlier
design put the file in =/tmp= to avoid leaving a stray file in the tree;
the result was the confirmed failure where the model narrated writing
the message to its handed =/tmp= path while the write never landed, and
portia then died with "no commit message" on a port that was otherwise
complete. Putting the file where the model already writes the port fixes
the writability; the stray-file worry is met instead by removing the
file after reading it and before the change check, so it never counts as
uncommitted work nor lands in the commit. The stub model in the tests
has no such scope, so it masked the bug - a test now pins the handed
path inside the port directory to keep it fixed.

The changelog-reference requirement lives in the prompts, not the
harness: =update.org= tells the model to cite the changelog for every
intermediate version and where to find them (this port's previous
commits, the upstream home page), exactly as the spec lists.

* the commit is keyed on the port path, not on the turn
The spec asks portia to commit when the desired state is reached, and to
pick up changes an interrupted run left on disk. So the trigger is
deterministic and lives in the harness: after the shape check, portia
asks the version control whether the port path has uncommitted changes
(=jj diff -s=, =git status --porcelain= scoped to the origin). Changes
present means commit; a clean port path means the desired state is
already committed - nothing to do, exit 0. This is the half the earlier
design got wrong: it keyed on "did this turn produce a message", so a
run that found the port already complete on disk (from an interrupted
predecessor) but wrote no message died with "no commit message" instead
of committing the stranded work.

Because the harness decides whether to commit, the model must not: its
job is to *always* write a message describing the port's resulting
state, even when the files already look finished on disk. The prompts
say so, and call out the update case by name, so the model never mistakes
"already on disk" for "nothing to do" - the mistake the confirmed
failure turned on. The message describes the commit's content, not the
session's activity; keeping it that way is what lets a port be driven to
completion over several interrupted runs and still read as one coherent
commit. A message is only required once changes exist: with a clean port
path portia exits 0 whether or not one was written.

* the ports tree must be a jj or git repository, checked first
A port is committed into the ports tree, so the tree - =PORTSDIR= for an
origin, the path's embedded ports dir for a path - must be under version
control. portia accepts either jj or git, detected by =.jj/= or =.git/=
at the tree root, and checks this before invoking the model so a
misconfigured run fails fast instead of burning a model turn only to
have nowhere to commit. A tree under neither is a hard error, in keeping
with the harness's fail-loud stance. Because the tree is resolved from
the argument, a path whose embedded tree is not a repository fails the
same way an origin under a non-repo =PORTSDIR= does.

jj is preferred when both are present - a colocated repo has both. The
spec asks for it: a jj change id names the commit stably, where a git
sha is opaque to the model, and a jj workspace has no =.git/= of its
own, so relying on git alone would miss those trees. Committing differs
by backend but the split is the same - jj snapshots the working copy and
commits the port path in one step, git stages then commits - and each
carries the model's message: jj through =-m= with the file's contents,
git through =-F=. Only the port's own path is committed, leaving any
unrelated working-copy changes in the tree.

The two backends locate the tree differently, and this matters because
the origin is relative to the tree, not to portia's own directory. =git
-C= runs inside the tree, so a bare origin resolves there. =jj -R= only
names the repo without changing directory: jj resolves file arguments
against the working directory, so a bare origin is read relative to
where portia was invoked and rejected as escaping the repo when that is
not the tree (=Invalid component ".."=). The origin is therefore handed
to jj as a =root:= fileset, which jj resolves against the tree root
wherever portia runs from.

* =new= reads detail from stdin
=portia new= reads free-form detail (version, home page, author, git
repo) from stdin and passes it into the prompt as context. stdin is a
sharp, testable channel for optional free-form input; the other
commands take none.

* =troubleshoot= diagnoses a build failure from the poudriere logs
The other two commands take no failure input, so the "current
standard" and "understand what the build consumes" lessons land in
=new= and =update= only as *prevention*. =troubleshoot= is the
*diagnostic* mode: it is the capability the confirmed failure showed was
missing - the successful run was handed a build log and asked to find
the root cause, which =new= and =update= never do. So its prompt
carries the same methodology as a procedure: read the exact error, trace
what the failing step consumes, find the current-standard mechanism by
prevalence, research the error class widely (bugzilla, forums, the port's
failure history), separate cause from trigger, then fix - migrating to
the standard mechanism where the port is on a broken one. The same
consensus-default rule applies: an obstacle the standard mechanism hits
is a problem to research and solve, not grounds to keep the port on the
minority scheme that happens to work.

The harness side is deliberately thin, reusing everything the other
commands established. =troubleshoot= resolves the port the same way,
requires the same complete-port shape (=Makefile=, =distinfo=,
=pkg-descr=), and commits the same way; a fix that changes the distfile
set regenerates =distinfo=, so requiring it costs nothing when it does
not. The one new piece is where the failure log lives: portia hands the
model =${POUDRIERE_URL}/data/latest-per-pkg/= as context and the model
navigates it to the port's most recent failure. =POUDRIERE_URL= defaults
to the project's public instance and carries the whole base URL, so an
instance laid out differently is overridden in one variable. Only
=troubleshoot= consults it; the diagnostic knowledge lives in the prompt,
not the harness, exactly as the porting knowledge does for the others.
