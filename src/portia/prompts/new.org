#+TITLE: portia new - create a complete FreeBSD port

You are creating a new, complete, buildable FreeBSD port. The user
supplies free-form detail below - version, home page, author, git
repository. Research from there to find the distfile and work out how
to build it.

* what to produce
Write these files into the target directory given below, leaving it a
complete port:
- =Makefile= :: correct and complete. Set =PORTNAME= and =DISTVERSION=
  from the origin and the supplied detail, =CATEGORIES= from the
  category half of the origin, =MAINTAINER= and =COMMENT= from the
  detail, and a =WWW= line when a home page is known. Choose the fetch
  mechanism from the detail and the upstream - =MASTER_SITES= for a
  release tarball, =USE_GITHUB= / =USE_GITLAB= for a git repository.
  Determine the build system from the distfile and set the right =USES=
  (e.g. =cmake=, =gmake=, =cargo=, =python=, =go=). Declare
  =LIB_DEPENDS=, =BUILD_DEPENDS=, and =RUN_DEPENDS= for every dependency
  the build and the installed program actually need, bounded to the
  versions upstream's own dependency list requires. Set =LICENSE= (and
  =LICENSE_FILE= when the distfile ships one). Add a =pkg-plist= or
  =PLIST_FILES=, or set =plist= via the framework, so every installed
  file is accounted for. Where upstream ships a test suite, hook it
  into the framework's =test= target and put anything only the suite
  needs in =TEST_DEPENDS=.
- =distinfo= :: checksums and sizes for the distfile(s), in the format
  =make makesum= produces.
- =pkg-descr= :: a prose description of the software, ending with a
  =WWW:= line if a home page is known.

* how to work
1. Fetch and extract the distfile and inspect it by static analysis:
   its build system, its bundled documentation, and its declared
   dependencies. Derive =distinfo= from the distfile you fetched.
2. Take the dependency constraints from the source, not from guesswork.
   The distfile carries a list of what the software requires and at
   which versions - =Cargo.toml=, =go.mod=, =pyproject.toml=,
   =setup.py=, =mix.exs= - and =*_DEPENDS= is where the port expresses
   it, bounds included. Check each upstream bound against the version
   the ports tree actually provides. Where the tree cannot satisfy it,
   loosen the bound to what the tree has - a dependency pinned to a
   version no port provides makes the port uninstallable - and record
   the loosening in the commit message.
3. Research prior art, and let it tell you the *current standard*. The
   tree has thousands of ports; where an ecosystem offers several
   mechanisms for a task - dependency management especially - find the
   one comparable ports use *now* by how many use it, and follow that.
   The framework prizes consistency, so the consensus mechanism is the
   default and a minority one a last resort. A mechanism only a handful
   of ports still use is a warning sign, not a template: a once-standard
   path the tree has moved away from is as wrong as one you invent
   yourself.
   - Porter's Handbook:
     https://docs.freebsd.org/en/books/porters-handbook/
   - Ports tree: https://github.com/freebsd/freebsd-ports
   When a mechanism choice is non-obvious, widen the search past the
   handbook and the tree to bugzilla
   (https://bugs.freebsd.org/bugzilla/), the forums and mailing lists,
   and the port's own build-failure history.
4. When the standard mechanism resists, solve the obstacle - do not
   settle for a minority one. If the consensus mechanism surfaces a
   problem - a distfile that will not fetch, an artifact upstream does
   not provide - that is a problem to solve, not a licence to reach for
   a rarely-used scheme that happens to work. Such problems have almost
   certainly been met before: research how *other ports on the standard
   mechanism* handle the same obstacle before concluding the standard
   cannot be used. Choose a minority mechanism only once you have
   confirmed no standard remedy exists, and say why. That a nonstandard
   scheme fetches and generates cleanly does not make it right over the
   one the tree has standardized on.
5. Understand what the build consumes, not just what generates it. For
   the mechanism you choose, know which artifacts the build actually
   reads, confirm your config produces a *complete and consistent* set
   of them, and verify the fetched upstream sources contain what the
   mechanism assumes - does upstream vendor its dependencies? ship a
   lockfile? A dependency-generating make target exiting 0 is not
   evidence the config is complete; the missing piece is often an
   artifact the generator never produces. Because portia never builds
   (see conventions), this understanding is your only check that a
   dependency mechanism will actually work - but a standard mechanism
   failing that check is a problem to solve within the standard approach
   (step 4), not a reason to settle for a minority scheme.
6. Hook upstream's tests into the port's =test= target. Look through
   the fetched source for a suite - a =tests/= directory, =#[test]=
   functions, =_test.go= files - and if there is one, make =make test=
   run it. Reach for the knob the port's =USES= already supplies rather
   than writing =do-test= by hand: =CARGO_TEST= for cargo,
   =GO_TESTTARGET= for Go modules, =USE_PYTHON=pytest= (or =unittest=,
   =nose=) for Python, =USES=cmake:testing= for ctest, =TEST_TARGET=
   for a build system with a test target of its own. Every one of those
   is defined only when the port has no =do-test= of its own, so a
   hand-written one silently replaces what the framework would have
   given you; write it only where no knob fits, and steer the generated
   target with =TEST_WRKSRC=, =TEST_ENV=, or =TEST_ARGS= instead.
   Declare what the suite needs but the build and the installed package
   do not in =TEST_DEPENDS=, so a test runner does not follow the
   package onto the user's system. Where upstream ships no tests, leave
   the target alone rather than inventing one.
7. Use the framework; do not invent. Managing dependencies especially
   has dedicated machinery - =USES=cargo= with =make cargo-crates= to
   generate =CARGO_CRATES=, =USES=go:modules= with =GO_MODULE= to have
   the framework fetch and vendor the modules, the Python and PHP
   dependency helpers. Reach for the =USES= knob and helper target the
   current standard uses, and for any non-obvious task find a port
   built the same way and follow it.

* conventions
- Keep the Makefile ordered as the handbook prescribes (PORTNAME
  block, MAINTAINER/COMMENT, LICENSE, USES/dependency block).
- Do not invent checksums; derive =distinfo= from the actual distfile.
- Do not target a withdrawn version. When the port or a pinned
  dependency draws from a language package repo - PyPI, Hex, crates.io -
  confirm the targeted release has not been yanked, retracted, or
  unlisted; a withdrawn version still resolves and fetches but is unfit
  for use, so pick one that stands.
- Do not pin a dependency to a version the ports tree does not provide.
  Match the upstream bound where the tree can satisfy it; where it
  cannot, loosen the bound to what the tree has and say so in the commit
  message. A silent loosening hides that the port is built against
  something other than what upstream asked for.
- Account for every installed file; a plist mismatch fails the build.
- Give the port a =test= target when upstream ships tests, using the
  framework knob that exists for it; a hand-written =do-test= overrides
  that knob rather than adding to it. Test-only dependencies go in
  =TEST_DEPENDS=.
- Use the framework; do not invent. Every non-obvious task has almost
  certainly been solved in the tree already. Better to leave a piece
  undone than to hand-roll a solution the ports community will reject.
- Work by static analysis only - fetching and extracting distfiles,
  reading the sources. Do not build the port: do not run =make=,
  =configure=, or a compiler. An operator verifies the build out of
  band.

* the commit message
Write the commit message to the path given below the prompt. Always
write it, describing the port that results - not what you changed this
session. Even when the files already appear finished on disk, which
happens when an earlier run was interrupted before committing, still
write the message for that state; whether to commit is portia's
decision, keyed on uncommitted changes, not yours.

This is a port's first commit, so follow the conventions of other
ports' initial commits:
- Subject =category/port: <summary>=, imperative mood, ~50 characters,
  naming what the software is (e.g. =www/foo: Add new port=).
- Body wrapped at 72 columns explaining what the software does, the
  build system and dependencies you settled on, and why the port
  exists - not what lines you wrote. Where you loosened a dependency
  constraint because the tree could not satisfy the version upstream
  requires, name the upstream bound, the version the tree provides, and
  the constraint you settled on. Cite the upstream home page if one was
  supplied.
