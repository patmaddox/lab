#+TITLE: yolo - an untrusted dev box for AI agents

Agents on yolo work as root: they build with poudriere, run bhyve
guests, and install what they like. Nothing on it is trusted. It is
cabled straight to rowdy's igb3, and rowdy lets it reach the internet
and nothing else. It holds no secrets but its own host keys and
password hashes.

* Build

On beastie, signed in to 1Password:

: redo yolo.be.zfs

The result is a ZFS send stream of a FreeBSD 15.1 pkgbase boot
environment with =dist/= applied, yolo's own packages installed, and
secrets from =op://Personal/yolo-secrets=. yolo's packages are the
ones =local_packages= in =yolo.conf= lists, and the build makes them
first. It holds password hashes and private keys, so it is mode 0600
and ignored by jj. Delete it after deploying.

* Install

yolo is installed from a USB stick. On beastie, signed in to
1Password:

: redo yolo-installer.img

This is a one-off, so =all= does not build it.
=infra/scripts/bsdinstall-stick.sh= makes it from the FreeBSD 15.1
memstick, as released, with a slice added that holds =yolo.be.zfs= and
the installer. It holds what the stream holds, so it is mode 0600 and
ignored by jj. Write it to the stick, here da0:

: dd if=yolo-installer.img of=/dev/da0 bs=1m

Boot yolo from the stick, choose Shell at the installer's welcome
screen, and run:

: mount -r /dev/ufs/installer /media
: sh /media/install.sh nda0

=install.sh= with no disk lists the disks. It asks you to type the
disk again, then lays out the disk as Auto (ZFS) on GPT (UEFI) does,
with no swap, as =stick.conf= asks. =dist/etc/fstab= finds the EFI
partition by the label bsdinstall gives it, efiboot0. Then it imports
the stream as yolo-<release>-<date>, e.g. yolo-15.1-2026-11-09, where
the date is the day the stream was built. It activates that BE and
destroys the stock default boot environment.

Remove the stick and reboot. Then wipe the stick, and delete
=yolo-installer.img= and =yolo.be.zfs=.

* Upgrade

A new BE is the whole update: base, ports, yolo's packages, and
=dist/= all come with it. Everything in =/usr/local= and =/etc= belongs
to the BE, so a package added by hand is gone after the next upgrade;
put it in =yolo.conf= instead. =zroot/jails= is outside the BE, so the
templates and jails carry over as they are; rebuilding a template is
separate, and yolo-jail's README says how.

On beastie, signed in to 1Password:

: just deploy-be

It builds the stream if needed, sends it over ssh to =bectl import= on
yolo, so it never lands on yolo's disk, and names the BE as the
installer does, with =-new= appended, e.g. =yolo-15.1-2026-11-09-new=.
Then it runs =bectl activate -t= on it. Reboot yolo as root:

: shutdown -r now

=activate -t= boots the new BE once; if it fails, the next reboot
returns to the old one. Once it works, make it permanent with
=bectl activate <name>=.

* Jails

yolo's jails, where agents run, are cloned from ZFS templates.
=zroot/jails/templates= holds the templates, and
=zroot/jails/instances= the jails. The yolo-jail tool, in
=src/yolo-jail=, builds the templates and clones jails from them. Its
README says how. The BE carries yolo's packages, one per tool in
=src/= and the jail configs. To try a change to one without a new BE,
=just push-pkg= builds them and copies them to =/tmp= on yolo, each
named =<name>-<version>.pkg=, where =pkg add= of one finds its
dependencies beside it. The next upgrade replaces what it added.

The =coding-agent= template is for jails that coding agents run in.
It has an =agent= user with unrestricted =doas=, so the agent
installs whatever else it needs.

The =yolo-jails= package, from =jails/=, installs each jail's config
in =/etc/jail.conf.d=. =jails/jails= lists the jails, each with its
template and the last octet of its address on 10.200.0.0/24, which
also numbers its epair. =jails/jail.conf.in= is the config they share.
Each jail has its own network stack, on an epair whose other end
joins =bridge0=, which puts it on yolo's /24.
To set up the jails, as root on yolo:

: yolo-jail-template coding-agent

=yolo-jail-template= creates =zroot/jails= and builds the template
=zroot/jails/templates/coding-agent@ready=, which every jail clones.
Run it once, and again only to rebuild the template.

Jails run no sshd. To use one, sign in to yolo, and as root:

: service jail onestart <name>
: jexec -l -U agent <name>
: service jail onestop <name>

The first start clones =zroot/jails/instances/<name>= from its
template, and makes =zroot/jails/instances/<name>/data=, a ZFS dataset
the jail runs itself. It has no mountpoint of its own, and the jail
may make, mount, and destroy datasets under it. For poudriere there,
set in =poudriere.conf=:

: ZPOOL=zroot
: ZROOTFS=/jails/instances/<name>/data/poudriere

To start a jail over, stop it, destroy its dataset and everything under
it, and start it again:

: service jail onestop <name>
: zfs destroy -r zroot/jails/instances/<name>
: service jail onestart <name>

Datasets meant to outlive a reset belong under =zroot/jails/data/<name>=,
and are given to the jail by adding them to its =zfs.dataset=.

The jails may run bhyve. They see =/dev/vmmctl=, their VMs under
=/dev/vmm=, =nmdm= consoles, and =tap= interfaces, by devfs ruleset 10
in =dist/etc/devfs.rules=. A VM's network is the jail's to arrange,
e.g. a bridge in the jail holding its epair and the VM's tap.

The jails' addresses:
- lab-1, lab-2, and lab-3: 10.200.0.11 to .13
- devops-1, devops-2, and devops-3: 10.200.0.21 to .23
