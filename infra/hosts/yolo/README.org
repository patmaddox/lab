#+TITLE: yolo - an untrusted dev box for AI agents

Agents on yolo work as root: they build with poudriere, run bhyve
guests, and install what they like. Nothing on it is trusted. It is
cabled straight to rowdy's igb3, and rowdy lets it reach the internet
and nothing else. It holds no secrets but its own host keys and
password hashes.

* Build

On beastie, signed in to 1Password:

: redo yolo.be.zfs

The result is a ZFS send stream of a FreeBSD 15.1 pkgbase boot
environment with =dist/= applied, yolo's own packages installed, and
secrets from =op://Personal/yolo-secrets=. yolo's packages are the
ones =local_packages= in =yolo.conf= lists, and the build makes them
first. It holds password hashes and private keys, so it is mode 0600
and ignored by jj. Delete it after deploying.

* Install

yolo is installed from a USB stick. On beastie, signed in to
1Password:

: redo yolo-installer.img

This is a one-off, so =all= does not build it.
=infra/scripts/bsdinstall-stick.sh= makes it from the FreeBSD 15.1
memstick, as released, with a slice added that holds =yolo.be.zfs= and
the installer. It holds what the stream holds, so it is mode 0600 and
ignored by jj. Write it to the stick, here da0:

: dd if=yolo-installer.img of=/dev/da0 bs=1m

Boot yolo from the stick, choose Shell at the installer's welcome
screen, and run:

: mount -r /dev/ufs/installer /media
: sh /media/install.sh nda0

=install.sh= with no disk lists the disks. It asks you to type the
disk again, then lays out the disk as Auto (ZFS) on GPT (UEFI) does,
with no swap, as =stick.conf= asks. =dist/etc/fstab= finds the EFI
partition by the label bsdinstall gives it, efiboot0. Then it imports
the stream as yolo-<release>-<date>, e.g. yolo-15.1-2026-11-09, where
the date is the day the stream was built. It activates that BE and
destroys the stock default boot environment.

Remove the stick and reboot. Then wipe the stick, and delete
=yolo-installer.img= and =yolo.be.zfs=.

* Upgrade

A new BE is the whole update: base, ports, yolo's packages, and
=dist/= all come with it. Everything in =/usr/local= and =/etc= belongs
to the BE, so a package added by hand is gone after the next upgrade;
put it in =yolo.conf= instead. =zroot/jails= and =zroot/pkg= are
outside the BE, so the jails and the templates' package repository
carry over as they are. Upgrading a jail is separate, and the Jails
section says how.

On beastie, signed in to 1Password:

: just deploy-be

It builds the stream if needed, sends it over ssh to =bectl import= on
yolo, so it never lands on yolo's disk, and names the BE as the
installer does, with =-new= appended, e.g. =yolo-15.1-2026-11-09-new=.
Then it runs =bectl activate -t= on it. Reboot yolo as root:

: shutdown -r now

=activate -t= boots the new BE once; if it fails, the next reboot
returns to the old one. Once it works, make it permanent with
=bectl activate <name>=.

* Jails

yolo's jails, where agents run, are each provisioned from a template,
and upgraded from it after. =zroot/jails/instances= holds the jails.
The yolo-jail tool, in =src/yolo-jail=, creates and upgrades them. Its
README says how. The BE carries yolo's packages, one per tool in
=src/= and the jail configs. To try a change to one without a new BE,
=just push-pkg= builds them and copies them to =/tmp= on yolo, each
named =<name>-<version>.pkg=, where =pkg add= of one finds its
dependencies beside it. =just install-pkg= also installs them all,
replacing the ones installed, which have the same versions. The next
upgrade replaces what either added.

A template is a package. =templates/= holds the packages jails
install, one directory each, and =templates/<name>= builds the package
=yolo-<name>=. It has three parts:

- =<name>.conf=, a shell fragment that sets =comment=, =packages=, the
  names of the packages it depends on, and =users=, one =<user>:<uid>=
  per line.
- =pkg-plist=, pkg's own list of the files and symlinks the package
  installs, with their owners and modes. See pkg-create(8).
- =dist/=, which holds them in the shape of the jail's root, as yolo's
  own =dist/= does for the BE.

pkg builds the package straight from =dist/=, with
=pkg create -p pkg-plist -r dist=, and only what the plist lists goes
in. On install and upgrade, the package makes each of its users that
is missing, with a group of the same name and id and unrestricted
=doas=. A jail is made by installing its template's package and
updated by upgrading it, so a change to a template reaches a jail
without resetting it.

=templates/pkg-repos= is no template. Its package, =yolo-pkg-repos=,
holds the jails' pkg repository configs: FreeBSD's, as yolo has them,
and one for =yolo=. Every template depends on it, so an upgrade
updates them too.

The =coding-agent= template is for jails that coding agents run in.
It has an =agent= user with unrestricted =doas=, so the agent
installs whatever else it needs. Its conf,
=templates/coding-agent/coding-agent.conf=, is:

#+begin_src sh
# Template for jails that coding agents run in. The agent has doas, so
# it installs whatever else it needs. git is here because every jail
# clones its repo from /git. pkg and yolo-pkg-repos are here so the
# jail can upgrade itself from the repositories.

comment="Template for yolo's coding-agent jails"

packages="
pkg
yolo-pkg-repos
git
doas
"

users="
agent:15000
"
#+end_src

Its =pkg-plist= lists its one file:

#+begin_src text
@comment Each file and symlink the package installs, from dist/. They
@comment belong to root:wheel, with the mode set here.
@mode 0644
/usr/local/etc/gitconfig
#+end_src

The package installs =dist/usr/local/etc/gitconfig= at
=/usr/local/etc/gitconfig= in the jail. Files belong to root:wheel
unless =@owner= and =@group= say otherwise, and a line such as
=@(root,wheel,0600) /usr/local/etc/foo= sets one file's owner, group,
and mode. A symlink is a symlink in =dist/=, listed like a file. To add
a package or a file to every =coding-agent= jail, add it here, run
=just push-templates=, and upgrade each jail.

The packages live in a pkg repository on yolo, at =/pkg/yolo=, outside
the BE. It belongs to you, and each jail sees it read-only at the same
path, as the repository =yolo=. On beastie, make it once:

: just pkg-init

Then build the packages, and sync the repository to yolo with rsync,
deleting what it no longer holds:

: just push-templates

A package is versioned by the time it was built. redo rebuilds it only
when its conf, its plist, or a file the plist lists changes, so a
jail's next upgrade picks up exactly what changed. A jail's agent may
also install packages from the repository itself.

The =yolo-jails= package, from =jails/=, installs each jail's config
in =/etc/jail.conf.d=. =jails/instances= lists the jails, each with
its template and its number. =jails/jail.conf.in= is the config they
share.

Each jail has its own network stack and its own /24,
10.200.<number>.0/24, on an epair to yolo. yolo is .1 on its end and
the jail is .2. yolo routes each jail's /24 and forwards it to rowdy,
which routes all of 10.200.0.0/16 back to yolo. Jails share no network
with each other, with yolo's link to rowdy, or with rowdy, and pf on
yolo drops what a jail sends from an address outside its /24.

Set a jail up before its first start, from beastie:

: just init-jail <name>

Or as root on yolo:

: yolo-jail-init <name>

It creates =zroot/jails/instances/<name>=, with FreeBSD's base and the
template's package from the repository, so it needs the package in
the repository and the jail's repo made. It makes the mountpoints for
what the jail's config mounts, and the datasets the jail needs. A jail
does not start until it is set up, and starting it sets nothing up,
so it starts quickly. =yolo-jail-init= makes only what is missing, so
running it again on a stopped jail gives it whatever a newer
yolo-jail adds.

Jails run no sshd. To use one, sign in to yolo, and as root:

: service jail onestart <name>
: jexec -l -U agent <name>
: service jail onestop <name>

=yolo-jail-init= also makes =zroot/jails/instances/<name>/data=, a ZFS
dataset the jail runs itself. It has no mountpoint of its own, and the
jail may make, mount, and destroy datasets under it. For poudriere
there, set in =poudriere.conf=:

: ZPOOL=zroot
: ZROOTFS=/jails/instances/<name>/data/poudriere

A jail is upgraded only when you upgrade it. After
=just push-templates=, upgrade a running jail's template package, and
whatever its new version needs, from beastie:

: just upgrade-jail <name>

Or as root on yolo:

: yolo-jail-upgrade <name>

=just upgrade-jail <name> -a=, or =yolo-jail-upgrade -a <name>=,
upgrades all of the jail's packages, including FreeBSD's base. A
jail's base must be no newer than yolo's, so upgrade yolo's BE first.
An upgrade replaces the template's files, so a change the agent made
to one of them is lost.

To start a jail over, stop it, destroy its dataset and everything under
it, set it up afresh, and start it again:

: service jail onestop <name>
: zfs destroy -r zroot/jails/instances/<name>
: yolo-jail-init <name>
: service jail onestart <name>

Datasets meant to outlive a reset belong under =zroot/jails/data/<name>=,
and are given to the jail by adding them to its =zfs.dataset=.

Each jail gets one git repo, which =jails/instances= names as
=<owner>/<repo>=. yolo keeps it at =/git/<owner>/<repo>.git=, and the
jail sees it there too, read-only. The jail's own repos are at
=/git/agent= in the jail and =/git/jails/<name>= on yolo, read-write.
Both are outside =zroot/jails/instances=, so a reset keeps them.
=yolo-jail-init= refuses to set a jail up until its repo exists.

=repos= lists the repos, each with its default branch, which a clone
checks out, and must list each repo that =jails/instances= names. On
beastie, make those that are missing and set their default branches:

: just git-init

It runs =doas yolo-git-init= on yolo, as yolo-jail's README says, so
the repos belong to you there. Run it again after changing =repos=.
=yolo-jail-init= makes the dataset for a jail's own repos.

Once a jail starts, its agent has a bare repo of its own for its
work, at =/git/agent/<owner>/<repo>.git=. yolo-jail's README says how.

The jails may run bhyve. They see =/dev/vmmctl=, their VMs under
=/dev/vmm=, =nmdm= consoles, and =tap= interfaces, by devfs ruleset 10
in =dist/etc/devfs.rules=. A VM's network is the jail's to arrange.
To give VMs addresses from the jail's /24, make a bridge in the jail
holding its epair and the VMs' taps, and give each VM an address in
the /24 with yolo's .1 as its router. Networks a jail NATs for itself
should come from outside 10.200.0.0/16.

The jails' networks:
- lab-1, lab-2, and lab-3: 10.200.11.0/24 to 10.200.13.0/24
- devops-1, devops-2, and devops-3: 10.200.21.0/24 to 10.200.23.0/24

* Git

beastie pushes repos to yolo and fetches the agents' work from the
jails' own repos, all over ssh as patmaddox. yolo holds no credentials
for them, and no git runs as root.

Make the repos that =repos= lists before their jails are set up, and
again after changing =repos=:

: just git-init

In the repo on beastie, add yolo, and each jail that has the repo:

: jj git remote add yolo patmaddox@yolo.p7x.dev:/git/patmaddox/lab.git
: jj git remote add lab-1 patmaddox@yolo.p7x.dev:/git/jails/lab-1/patmaddox/lab.git

Then push to yolo, and fetch from the jails:

: jj git push --remote yolo -b trunk
: jj git fetch --remote lab-1

In the jail, as agent, clone the repo, and add the agent's own repo,
which beastie fetches from, as a remote to push to:

: git clone /git/patmaddox/lab.git ~/lab
: cd ~/lab
: git remote add agent /git/agent/patmaddox/lab.git
: git push agent <branch>

A jail's repo is the jail's to write, so treat what beastie fetches
from it as untrusted. jj does not track a new remote bookmark, so a
jail that pushes trunk leaves beastie's trunk alone, as trunk@lab-1.
Read a bookmark's diff before checking it out on beastie. Files such
as =.claude/=, =CLAUDE.md=, =Justfile=, and =*.do= run code there.
