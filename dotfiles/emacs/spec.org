* Overview
This spec defines functionality that I want to add to my emacs
configuration, which is contained in this directory.

Your job is to write elisp code that meets the requirements.

* Rules
Your response MUST include a <promise> tag indicating the result.
This is the only structured output requirement - you may output other
text as needed to do your work.

All third-party code must be stored in the `vendor/` dir.

* Development process
When the prompt is "continue":
1. Study this entire spec
2. If any TODO tasks lack both :ready: and :blocked: tags, do "plan"
3. Otherwise, do "dev"
** Selecting the best available task
If a specific task is provided in the prompt, do that one.

If not, choose a task that matches ALL of the following criteria

- is in state TODO
- has :ready: tag
- you are confident you can complete it
- has no dependencies on other tasks

When choosing among the available tasks, prioritize harder / more
uncertain tasks first. We don't want to knock out a bunch of easy
stuff and then get stuck.

If you cannot find a task meeting any of these criteria, output:
    <promise>error: no matching tasks</promise>

If all of the tasks in the file are marked DONE, output:
    <promise>ok</promise>

** Requirements analysis
This is a separate role from implementation. The goal is to make
tasks well-defined enough that claude code can implement them
autonomously.

When the prompt is "plan", perform requirements analysis:
1. Study this entire spec, including DONE tasks
2. Check all tasks for =:FEEDBACK:= drawers. If any task (including
   DONE) has feedback, revert it to TODO, incorporate the feedback
   into the plan, and remove the drawer.
3. Find ONE TODO task that still needs a :ready: tag (skip :blocked: tasks)
3. Analyze requirements, clarify ambiguities, break into subtasks if
   the work has distinct steps or components
4. When a task (or subtask) has clear enough requirements for
   implementation, add the :ready: tag
5. Refer to existing tasks in the file for how to structure new ones
6. Subtasks are org sub-headings under the parent task with their own
   TODO state

Do NOT write code during requirements analysis. Only update spec.org.

Ignore :blocked: tasks entirely — they do not count when determining
whether all tasks are planned.

If all non-hold TODO tasks already have :ready: tag, output:
    <promise>ok</promise>

Before analyzing a task, check for answered questions. Answered
questions have a response after the checkbox text, e.g.:

- [X] what language are we using? elixir

Incorporate each answer into the task requirements and remove the
question item. Remove the =:QUESTIONS:= drawer when all questions
are resolved.

If you cannot make a task ready (e.g. ambiguous requirements that
need human input), add questions in a =:QUESTIONS:= drawer:

:QUESTIONS:
- [ ] what jail name should the wrapper script use?
- [ ] where should the script be installed?
:END:

Add the :blocked: tag to the task so it does not block progress.
A task must never be marked :ready: if it still has open questions.

Then output:
    <promise>error: reason</promise>

When you finish planning a task, output:
    <promise>continue</promise>

** Working on tasks
Your work product is elisp code in one or more of the following places:
- init.el
- lisp/
- vendor/

If you cannot complete a task:
1. Update the task in spec.org to have :error: tag
2. Add a sub-heading to the task with the error information
3. Output <promise>continue</promise> and nothing else

When you complete a task:
1. Update the task type in spec.org to DONE
2. Output <promise>continue</promise> and nothing else
