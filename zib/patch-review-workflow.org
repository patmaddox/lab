#+TITLE: patch review workflow

Motivation: Develop an effective workflow for working with LLMs, where
they can produce commits in isolated environments, and I can review
and apply them.

Inspiration: Mailing-list-driven workflow as found in Linux, OpenBSD,
PostgreSQL. All of those projects work with highly concurrent,
untrusted developers - which is essentially what it's like to work
with a coding agent.
* Goal
The basic goal here is to produce =trunk= as a mostly-linear series of
commits applied from a mailing list.

The mailing list is also a series of linear commits. Contributors
(mostly LLMs, but could be anyone) post messages to the mailing list,
including their patches. They submit messages by publishing a branch,
which serves as a moderation queue. Moderator cherry-picks messages
into the mailing list archive.

From there, Maintainer reviews the commits and integrates them into
=trunk=, perhaps responding to them directly on the mailing list.

Agents rebase their own mail branches onto the canonical mail branch,
dropping any messages that have been integrated into the archive.
* Async
One of the most important problems this solves is by making all
communication async. Right now I can use a coding agent to review a
doc, but I have no way to queue work for the agent to do, or treat its
responses as a queue.
* Roles
** Contributor
Contributors track two branches: =trunk= and =mail=. They produce new
commits on top of each of those branches. Commits on top of =trunk=
are patches that will be submitted for consideration. Commits on top
of =mail= are messages that will be sent to the moderation
queue. Contributors submit patches by publishing their =mail=
branch. Mailing list moderator then cherry-picks commits from
contributor branches into canonical =mail= branch. The contributor's
trunk-based branch is their private source and is never pulled.

When a contributor begins a work session, they fetch upstream =trunk=
and =mail= and rebase their local branches. Commits that have been
integrated into upstream branches are automatically dropped from the
local branches, e.g. using =jj rebase --skip-emptied=. Maintainers
might modify commits, in which case contributor will need to drop the
superseded commits themselves.
** Moderator
Moderators review incoming messages in published =mail= branches, and
cherry-pick them into the canonical =mail= branch to produce the
devlist archive.

Criteria for accepting or rejecting messages are out of scope.

Process for rejecting messages is out of scope.
** Reviewer
Reviewers read patches on the mailing list and provide feedback by
responding on the mailing list. Feedback goes to the moderation queue
like any other message. Reviewers may participate in any discussion on
the list.
** Maintainer
Maintainers decide which patches reach trunk. They apply patches from
the list, and if the patch is acceptable, move =trunk= to the newly
applied patch and push it.

Maintainer may also reject patches on the list. Resolution of a patch
will always be either to apply or reject. Maintainer may revise a
patch before applying.
* Process
** Contributor
Getting up to date:
- Fetch =trunk= and =mail= branches from =upstream= repo
- Rebase local work onto =upstream/trunk= and drop superseded commits
- Rebase local mail onto =upstream/mail= and drop superseded commits

Developing new work:
- Identify new work to be done via new messages on the list
- Develop new work
- Compose new message to the list (including patches) and publish to
  =submissions= repo
** Moderator
- Fetch devlist commits from =submissions= repo
- Verify that the commits only add maildir messages and make no other
  changes.
- Decide which messages to cherry-pick or reject
- Cherry-pick commits to =mail= branch
- Publish mail branch
** Reviewer
- Fetch the list
- Respond to messages, publishing new messages the same way a
  contributor does
** Maintainer
- Fetch mailing list
- Read new messages
- Apply patches to =trunk= without moving bookmark
- Review and test, revise if needed
- Accept (move trunk and push) or reject (abandon)
- Post resolution to list
* Tech notes
** mailing list doesn't have to be a real mailing list
For my purposes, the mailing list is probably just a maildir in a
dedicated branch. I don't need an actual mailing list infrastructure
at this point.
** maildir doesn't rename files
notmuch by default renames files to indicate if they've been
seen. This will be disabled by setting =maildir.synchronize_flags
false=. Once a message is added to the list, it does not get renamed.
** maintainer can post directly to the list
Trusted members don't have a moderation queue.
* Contributor workspace setup
Agents run in a repeatable setup, given the tools they need to do
development work. Essentially they are an automated developer, with
minimal permissions.

Contributor jail workspace has two git remotes:

- =/data/lab.git= upstream remote (ro, enforced by mount)
- =/data/lab-submissions.git= submissions remote (rw)

The contributor development workspace is a FreeBSD jail, with data
dirs provided by nullmount.

The jail workspace clones =lab= to =~/lab/default.jj= jj
workspace as =upstream= remote, and adds =lab-submissions= as
=submissions= remote. =~/lab/mail.jj= jj workspace contains the
mailing list, and is based off of =mail@upstream=.

Contributors only push mail commits to =agent@submissions=, and never
push any other branches.

Currently there is only one agent workspace, so there is no risk of
collision, overwrites, or concurrency issues.

notmuch config
- =database.mail_root ~/lab/mail.jj/maildir=
- =maildir.synchronize_flags false=
- =database.path ~/.notmuch/=

* Shared repo setup
Two repos shared across jails:
- =/jails/share/lab.git= owned by host user =patmaddox=
- =/jails/share/lab-submissions.git= owned by host user =claude=

This matches the ownership required to be writable within the
jails. The jails create users with same uid and name as on the
host. These are defined in the respective jail definition dirs.

Both are world readable.

git repo setup:

#+BEGIN_SRC
$ doas zfs create zroot/jails/share
$ doas zfs create zroot/jails/share/lab.git
$ doas git -C /jails/share/lab.git/ init --bare -b trunk
Initialized empty Git repository in /jails/share/lab.git/
$ doas chown -R patmaddox:patmaddox /jails/share/lab.git/
$ doas zfs create zroot/jails/share/lab-submissions.git
$ doas git -C /jails/share/lab-submissions.git/ init --bare
Initialized empty Git repository in /jails/share/lab-submissions.git/
$ doas chown -R claude:claude /jails/share/lab-submissions.git/
#+END_SRC
