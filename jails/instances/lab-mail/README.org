#+TITLE: lab-mail

A mail relay for p7x.dev. lab-mail holds the Fastmail credentials and
is the only thing that talks to Fastmail. Agents send and read mail
through it over loopback. spec.org has the design.

* how it works
lab-mail shares beastie's addresses (=ip4 = inherit=), like the
client jails. Its services listen on 127.0.0.1, which every such jail
on beastie reaches and nothing off beastie does. Clients reach them
over that loopback, never through a shared filesystem.

Two host directories are mounted into the jail, and into no other:
- =/jails/data/lab-mail/secrets= at =/data/secrets=, read-only. It
  holds =mail-creds=, the Fastmail login.
- =/jails/data/lab-mail/mail= at =/data/mail=, read-write. It holds
  the mail state, which survives a rebuild of the jail.

The credentials never leave =/data/secrets=. Only the services that
talk to Fastmail can read them, as members of the =mailcred= group.

** sending
#+BEGIN_EXAMPLE
client --SMTP--> smtprelay 127.0.0.1:2525 --SMTPS--> smtp.fastmail.com:465
#+END_EXAMPLE

smtprelay is the only way out. rc(8) starts it when the jail starts,
under daemon(8) as the user =smtprelay=; its config is
=/usr/local/etc/smtprelay/smtprelay.ini=. Before it starts,
=remotes.env= reads =mail-creds= and passes the Fastmail login to it
in its environment.

A client connects without logging in. smtprelay checks the envelope
sender and each recipient against the allowlists in =smtprelay.ini=,
and refuses any address that is not on them. It then logs in to
Fastmail and relays the message while the client waits, so the
client gets Fastmail's answer. Nothing is queued: a message that
fails is not sent, and the client must send it again.

** fetching
#+BEGIN_EXAMPLE
imap.fastmail.com:993 lists --IMAPS--> mbsync --> /data/mail/maildir/lists
#+END_EXAMPLE

A Fastmail rule files list mail into the folder =lists=. Once a
minute, the jail's cron(8) runs the fetch job,
=/usr/local/libexec/lab-mail/fetch=, as the user =mbsync=. The job
is in =/etc/cron.d/lab-mail=, not in a crontab, so =crontab -l= does
not show it. lockf(1) skips a run while the previous one is still
going.

The fetch job runs mbsync with =/usr/local/etc/mbsyncrc=, which logs
in to Fastmail with =mail-creds= and pulls only new messages into the
maildir. It never changes anything on Fastmail, and never removes a
message from the maildir. mbsync keeps its sync state in
=/data/mail/mbsync=. mbsync creates the new files readable only by
itself, so the job then makes them readable by everyone, for Dovecot.

** reading
#+BEGIN_EXAMPLE
/data/mail/maildir/lists --> Dovecot 127.0.0.1:2143 --IMAP--> client
#+END_EXAMPLE

rc(8) starts Dovecot when the jail starts; its config is
=/usr/local/etc/dovecot/dovecot.conf=. It serves the maildir as the
mailbox =lists=, beside an empty INBOX, and accepts any user name and
password. Every login runs as the user =vmail=, which can read the
maildir but not write it, and keeps Dovecot's indexes in
=/data/mail/dovecot=. The ACL in =dovecot-acl= makes every mailbox
read-only, so a client cannot flag, add, or delete mail.

Dovecot never talks to Fastmail. A client reads only what the last
fetch brought, so new list mail reaches it within a minute or two,
and reading keeps working while Fastmail is down.

** logs
Each service logs through syslogd(8) in the jail, to a file of its
own under =/var/log/lab-mail/=, and all of them to =/var/log/maillog=:
- =smtprelay.log=: each session, with the client, the envelope, and
  Fastmail's reply.
- =fetch.log=: each pull that brought mail, and every fetch failure.
- =dovecot.log=: each IMAP login, and every error.

A fetch that brings nothing logs nothing, so a quiet =fetch.log= is
normal. The routing is in =/etc/syslog.d/lab-mail.conf=, and
newsyslog(8) rotates the files daily and keeps a week. From beastie:
#+BEGIN_EXAMPLE
doas tail -f /jails/instances/lab-mail/var/log/lab-mail/fetch.log
#+END_EXAMPLE

* setup
The operator stores the Fastmail login and app password on the host,
in =/jails/data/lab-mail/secrets/mail-creds=. They never enter the
repo. The jail mounts the directory read-only at =/data/secrets=, and
no other jail mounts it.

=mail-creds= holds two lines: the Fastmail login on the first, and an
app password with IMAP and SMTP access on the second. Each line is
taken whole, whatever it contains.

Inside the jail, only members of the =mailcred= group (gid 15100) may
read it. The host knows the group only by number:
#+BEGIN_EXAMPLE
mkdir -p /jails/data/lab-mail/secrets
cd /jails/data/lab-mail/secrets
printf '%s\n' 'login@example.com' 'app-password' > mail-creds
chown -R 0:15100 .
chmod 0750 .
chmod 0640 mail-creds
#+END_EXAMPLE

=/jails/data/lab-mail/mail/= holds mail state that must survive a
rebuild of the jail. The jail mounts it read-write at =/data/mail=.
The operator creates it and its subdirectories before the jail first
starts. The host knows the owners only by number, from
=instance.conf=: 15102 is mbsync, 15103 is vmail.
#+BEGIN_EXAMPLE
install -d -m 0755 /jails/data/lab-mail/mail
install -d -o 15102 -g 15102 -m 0755 /jails/data/lab-mail/mail/maildir
install -d -o 15102 -g 15102 -m 0700 /jails/data/lab-mail/mail/mbsync
install -d -o 15103 -g 15103 -m 0700 /jails/data/lab-mail/mail/dovecot
#+END_EXAMPLE

* operate
Like the other instances; see =jails/README.org=:
#+BEGIN_EXAMPLE
just build
just install
just start
#+END_EXAMPLE

The build starts the jail before it installs the config, so restart
the jail after a build that changes the config.

* check
=just check= checks that lab-mail is set up and running. It prints
one line per check, ok or FAIL, and exits non-zero if any check
fails:
#+BEGIN_EXAMPLE
$ just check
ok the jail is running
ok /data/secrets/mail-creds exists
...
FAIL smtprelay is running
FAIL smtprelay accepts connections on 127.0.0.1:2525
...
#+END_EXAMPLE

It checks the jail, =mail-creds= and who can read it, the owners of
the mail state directories, that syslogd, cron, smtprelay, and
Dovecot are running, that smtprelay and Dovecot accept connections,
that a fetch succeeded within the last five minutes, and that the log
files exist. The fetch job touches =/data/mail/mbsync/last-fetch=
after each successful pull, so a quiet list still passes. The
check only reads, so it is safe to run at any time;
=/usr/local/libexec/lab-mail/check= in the jail does the work.

When a check fails, the service's log under =/var/log/lab-mail/=
usually says why.
