#+TITLE: lab-mail: the mail hub for the lab-devel list

artifact: a jail instance in this dir, built and operated like the
other instances in =jails/instances=, plus the mail clients that
lab-claude needs to use it.

goal: the lab-devel list lives on lab-mail, synced both ways with
Fastmail. Every host that uses the list treats lab-mail as its
upstream server: it syncs the list over IMAP and posts to it over
SMTP. Agents can read the list and add to it, and they can do nothing
else to it. Only lab-mail holds the Fastmail credentials and talks to
Fastmail. Clients reach lab-mail over the network, never through a
shared filesystem, so they need not run on the same host as lab-mail.

provider: p7x.dev and lists.p7x.dev are hosted on Fastmail.
- IMAP: imap.fastmail.com, port 993, implicit TLS.
- lab-mail logs in with the Fastmail account's login and one app
  password with IMAP access. Only mbsync uses them.
- The account is the list's own. The list's addresses are
  =lab-devel@p7x.dev=, =lab@lists.p7x.dev=, and
  =freebsd-ports@lists.p7x.dev=. Mail to any of them lands in INBOX.
  No Fastmail rule files it elsewhere.
- Fastmail's folder =Archive= is the account's archive folder. Over
  IMAP it carries the =\Archive= special-use flag.
- The account's folders =Next= and =Later= are plain folders. The
  operator creates them once on Fastmail.

the list: the folders INBOX, =Next=, =Later=, and =Archive= of the
Fastmail account.
- A message posted to the list lands in INBOX. Pat moves a message
  that needs work to =Next= when it comes up soon, or to =Later= when
  it can wait. Archiving a message moves it to =Archive=. A message
  that needs no answer is archived.
- The folder a message is in is its state. That state lives in the
  list data, not in any one client, so Fastmail and every client see
  it, and a move on Fastmail's web interface counts like any other.
- The list holds every message from the jj maildir that carried it
  before, imported once by the operator, so old threads keep their
  context and replies to them still thread.
- Pat removes a message he does not want on the list by deleting it,
  which his login may do. There is no moderation queue.
- Any other folder of the account is not part of the list. Pat may
  make one on Fastmail for anything else, and it never reaches
  lab-mail.

rights: who may do what to the list.
- Anyone who can reach lab-mail may post to the list over SMTP, with
  no login. Posting only adds a message. It cannot change or remove
  one already there.
- Anyone may read the list over IMAP. Any user name logs in with any
  password, and that login may list, fetch, search, and IDLE, and
  nothing else. Dovecot's ACL opens every mailbox read-only for it:
  its attempts to set flags or expunge change nothing, and its
  attempts to append, copy into a mailbox, or move fail. So it cannot
  archive or delete a message, and it cannot mark one read for anyone
  else.
- IMAP has no anonymous mode, so an agent logs in as its own address,
  such as =claude@p7x.dev=, with any password.
- Two logins may change the list: =pat@p7x.dev= and =mbsync=. Each
  must give the password in =imap-users=, and a wrong one fails. They
  may set flags, append, copy, move, and expunge, so Pat archives and
  deletes, and mbsync syncs with Fastmail. mbsync may also create a
  folder, so it can bring one over from Fastmail.
- These rights are enforced by Dovecot's ACL, not by file
  permissions. Dovecot's user can write the whole maildir, so a fault
  in the ACL config would let every login change the list. Steps 7
  and 8 of the acceptance test check the rules.

access:
- lab-mail uses =ip4 = inherit=, like the client jails. A jail with
  its own address has its own 127.0.0.1, which the other jails cannot
  reach.
- OpenSMTPD listens on 127.0.0.1:2525 for SMTP, and Dovecot listens
  on 127.0.0.1:2143 for IMAP. Neither listens on an external address
  or on a standard port (25, 587, 143, or 993), so no tool finds them
  there by default.
- So beastie, and every jail on it that uses =ip4 = inherit=, can use
  lab-mail, and nothing off beastie can. That is the security
  boundary. No pf rules are needed.
- Clients do not authenticate to post. What a client may do to the
  list once it is there depends on its IMAP login (see rights).
- No TLS between clients and OpenSMTPD or Dovecot. The traffic stays
  on loopback.

credentials: the operator stores three files on the host, in
=/jails/data/lab-mail/secrets/=. They never enter the repo.
- =mail-creds= holds the Fastmail login on its first line and the app
  password on its second. Each line is taken whole, so nothing
  depends on where a space falls in it. Only mbsync can read it.
- =imap-users= holds the logins that may write the list, each with a
  password hash: =pat@p7x.dev= and =mbsync=. Only Dovecot's auth
  process can read it.
- =mbsync-imap= holds the password of mbsync's own Dovecot login.
  Only mbsync can read it.
- Pat keeps the password for =pat@p7x.dev= on beastie, in
  =~/.config/lab-mail/password=, which only he can read. lab-mail
  holds only its hash.
- The directory is nullfs-mounted read-only into lab-mail, and into
  no other jail.
- mbsync refuses to start a sync unless both lines of =mail-creds=
  are present and not empty.
- The instance documents how the operator stores each file.

posting:
- Software: OpenSMTPD (mail/opensmtpd).
- OpenSMTPD never relays. It delivers to the list and nowhere else,
  so nothing a client posts leaves lab-mail except as a message that
  mbsync copies into a Fastmail folder.
- It accepts any envelope sender.
- It sorts each envelope recipient (RCPT TO) into one of three kinds:
  - The list's addresses are delivered to the list. Adding one is a
    one-line change to the instance's config.
  - A known address is accepted and discarded: =pat@p7x.dev=,
    =pat@patmaddox.com=, and =claude@p7x.dev=. The list is where
    everyone reads mail for these addresses, so a reply to all lands
    once, on the list. Adding an address is a one-line change to the
    instance's config.
  - Any other recipient is refused with a 5xx reply to its RCPT TO.
- A message with any refused recipient is posted to no one. The
  client abandons it on the refusal (see clients).
- OpenSMTPD parses the header of each message before it answers the
  client's DATA. It refuses with a 5xx reply a message whose header
  holds a line that is neither a field nor the continuation of one.
  So a client that sends something other than a mail message learns
  it while it is still connected, and nothing reaches the list.
- OpenSMTPD gives a Message-ID and a Date to a message that lacks
  them, as it does for any post on a loopback listener. So every
  message on the list can be threaded and sorted.
- A message to one of the list's addresses lands on the list once,
  whatever known addresses it is also sent to, with its To and Cc
  unchanged. A message to several of the list's addresses lands once
  for each, and notmuch shows it once, since the copies share a
  Message-ID. OpenSMTPD adds a Received header and any missing
  Message-ID or Date, Dovecot adds Return-Path and Delivered-To, and
  nothing else is changed. Who a message was addressed to is read
  from its To and Cc. Delivered-To names the list address each copy
  was delivered for, and a Bcc leaves no trace.
- OpenSMTPD hands each message for the list to Dovecot over LMTP, on
  a unix socket inside the jail, and Dovecot delivers it to INBOX.
  OpenSMTPD never opens the maildir.
- OpenSMTPD answers the client's DATA once the message is in its
  queue. A delivery that fails is retried from the queue, so a message
  posted while Dovecot is stopped lands when Dovecot is back. A
  delivery Dovecot refuses for good is logged, and its bounce is
  discarded like any other mail to a known address.

reading:
- Software: isync (mail/isync) for mbsync, and Dovecot (mail/dovecot)
  for IMAP and LMTP.
- Dovecot is the only program that writes the list. Every change to
  it, a posted message, a sync from Fastmail, or a move or deletion by
  Pat, goes through Dovecot, as Dovecot's user.
- The maildir lives in =/jails/data/lab-mail/mail/=, mounted
  read-write into lab-mail only, so a rebuild of the jail keeps the
  list. Dovecot's user owns it.
- The operator creates that directory and its subdirectories on the
  host before the jail starts, as with the credentials. The jail does
  not create anything on the host.
- Dovecot serves the list as the mailboxes INBOX, =Next=, =Later=,
  and =Archive=, as on Fastmail. INBOX is a folder of the maildir like
  the others. Every
  login sees the same mailboxes, and Dovecot's ACL gives each login
  the rights in the rights section.
- Dovecot serves IMAP and LMTP only. It does not run POP3 or
  submission, and its LMTP listens only on its socket inside the
  jail.
- Reading and posting keep working while Fastmail is down.

sync with Fastmail:
- mbsync in lab-mail syncs INBOX, =Next=, =Later=, and =Archive=
  both ways between Fastmail and Dovecot, as an IMAP client of each,
  and no other folder. It logs in to Dovecot on 127.0.0.1:2143 as =mbsync=, with
  the password in =mbsync-imap=. It never opens the maildir.
- New messages, flag changes, moves, and deletions travel in both
  directions on the next run.
- mbsync uses =Expunge None= and =Remove None=. It never expunges a
  message or removes a folder on either side. A message expunged on
  one side is only marked =\Deleted= on the other, so Fastmail keeps
  every message ever posted, and a mistaken deletion on lab-mail can
  be undone from there.
- mbsync uses =Create Near=. The folders come from Fastmail: one of
  the list's folders that Dovecot lacks is created on Dovecot at the
  next run, and mbsync never creates a folder on Fastmail. Dovecot
  creates no folder of its own.
- The jail's cron(8) runs the sync job once a minute, from a file in
  =/etc/cron.d=, as mbsync's user, so it is not in any user's
  crontab. A run that starts while the previous one is still going
  exits at once.
- The sync job records the time of its last successful run, so a
  check can tell a sync that stopped from a list that is quiet.

logs:
- Every service in lab-mail logs through syslogd(8) in the jail:
  OpenSMTPD, the sync job, and Dovecot. Each has a file of its own
  under =/var/log/lab-mail/=: =smtpd.log=, =sync.log=, and
  =dovecot.log=. They also land together in =/var/log/maillog=, as
  all mail logs do by default.
- OpenSMTPD logs each session: the client, the envelope, each
  recipient's fate, and each delivery to Dovecot. The sync job logs
  each run that moves mail, with mbsync's counts, and every failure.
  Dovecot logs each login, each LMTP delivery, and every error.
- newsyslog(8) rotates the files daily and keeps a week, as it does
  =/var/log/maillog=.
- syslogd in lab-mail opens no network socket. The jail shares
  beastie's addresses, so a socket would contend for UDP port 514
  with every other jail's syslogd, and nothing sends lab-mail logs
  over the network.

check:
- =just check=, run on beastie in the instance's directory, checks
  that lab-mail is set up and running. It exits 0 only if every check
  passes. It prints one line per check, saying ok or FAIL and what it
  checked, so the operator sees what is wrong.
- It checks that:
  - the jail is running;
  - =mail-creds= is present and neither of its lines is empty;
  - =imap-users= has entries for =pat@p7x.dev= and =mbsync=, and
    =mbsync-imap= is not empty;
  - each secret is readable by its reader and by no other service
    user;
  - the mail state directories exist with the owners the README
    gives;
  - syslogd, cron, OpenSMTPD, and Dovecot are running;
  - OpenSMTPD accepts connections on 127.0.0.1:2525, and Dovecot on
    127.0.0.1:2143;
  - OpenSMTPD's queue holds no message older than five minutes;
  - the last successful sync was within the last five minutes;
  - each log file exists.
- The check only reads. It changes nothing in the jail and posts no
  mail, so it is safe to run at any time.

clients: beastie, for Pat, and lab-claude, for the agent. Both are set
up the same way and differ only in the login.
- Packages: mail/isync, mail/msmtp, and mail/notmuch on both hosts.
- Each user's mail root is =~/mail/<login>=, such as
  =~/mail/pat@p7x.dev=. It holds the list's folders, INBOX, =Next=,
  =Later=, and =Archive=, and the user's own =sent=, which is never
  synced.
- notmuch indexes the mail root under the profile =lab-mail=, which
  =dotfiles/notmuch= installs. =notmuch new= never contacts lab-mail,
  so it works the same while lab-mail is down. It indexes =Change-Id=
  as =changeid:= and ignores mbsync's state files. Its post-new hook
  derives every tag from the mail root, so a rebuild of the database
  gives the same tags:
  - sent: mail from the user;
  - replied: other mail the user has answered, named in the
    In-Reply-To of the user's mail;
  - inbox: other mail in INBOX that the user has not answered;
  - next, later, and archived: mail in =Next=, =Later=, and
    =Archive=.
- Flag sync is on for a login that may write the list, so unread,
  flagged, and replied follow the list's flags. It is off for a
  read-only login, whose flags would never reach lab-mail.
- mbsync syncs the list's folders with lab-mail at 127.0.0.1:2143,
  only when the user runs it, and no other folder.
  - On beastie it logs in as =pat@p7x.dev=, with the password from
    =~/.config/lab-mail/password=, and syncs both ways with =Expunge
    Both=, so Pat's moves and deletions take effect on lab-mail.
    Fastmail still keeps every message.
  - On lab-claude it logs in as =claude@p7x.dev= and only pulls,
    with =Expunge Near=, so the local copy follows lab-mail.
- msmtp posts through 127.0.0.1:2525 with no login and no TLS, as
  =pat@p7x.dev= on beastie and =claude@p7x.dev= on lab-claude. When
  the server refuses any recipient or the message, msmtp posts
  nothing and exits non-zero with the server's reply, so the whole
  message is abandoned.
- =dotfiles/notmuch= ships samples of the profile's config and of
  the mbsync and msmtp configs, with =you@p7x.dev= for the login, and
  documents the commands to sync and to post. It installs no config
  itself; each host installs its own, with its login. lab-claude
  ships its own and documents them in its README.
- The agent searches and reads the local index, not IMAP.
- =just check= in =dotfiles/notmuch=, run as the user on any
  host, checks that login's client before it is used: mbsync logs in
  and lists the list's folders, a dry run of the sync succeeds, the
  profile has its config, hooks, and database, and msmtp reaches
  lab-mail from the profile's address. It prints one line per check,
  ok or FAIL, and exits 0 only if every check passes. It changes
  nothing and posts no mail.

acceptance test: run from lab-claude, except where a step says
beastie.
1. The agent posts a message with msmtp to =lab-devel@p7x.dev= and
   =pat@p7x.dev=, and msmtp exits 0. Exactly one file for its
   Message-ID lands in lab-mail's INBOX, and its To and Cc are as
   sent.
2. Within two minutes, the message is in INBOX on Fastmail.
3. A message sent to Fastmail from outside lab-mail, to
   =lab-devel@p7x.dev=, reaches the agent's mbsync and
   =notmuch search= within two minutes.
4. A message to =lab-devel@p7x.dev= and =someone@example.com= is
   refused at RCPT TO for =someone@example.com=. msmtp exits non-zero
   and nothing lands on the list.
5. A message with a header line that is not a field is refused at
   the end of DATA. msmtp exits non-zero and nothing lands on the
   list. A message with no Message-ID, posted with msmtp
   =--set-msgid-header=off=, lands on the list with one.
6. With Dovecot stopped, a message posted to the list is accepted,
   and it lands in INBOX within two minutes of Dovecot starting
   again.
7. Logged in as =claude@p7x.dev=, an IMAP STORE of =\Deleted=
   followed by EXPUNGE on INBOX changes nothing, and an APPEND to
   INBOX fails. The message stays in place, its flags unchanged, in
   lab-mail's maildir and on Fastmail.
8. A login as =pat@p7x.dev= or =mbsync= with a wrong password fails.
9. On beastie, =just check= exits 0.
10. On beastie, with OpenSMTPD stopped, =just check= exits non-zero
    and a FAIL line names OpenSMTPD.
11. On Fastmail, Pat moves a message from INBOX to =Archive=. Within
    two minutes, it is in =Archive= and not in INBOX on lab-mail.
12. Logged in as =pat@p7x.dev=, Pat moves a message from INBOX to
    =Archive= on lab-mail. Within two minutes, it is in =Archive= and
    not in INBOX on Fastmail. The same holds for =Next= and =Later=,
    and for a move back to INBOX.
13. On lab-claude as the agent, =just check= in =dotfiles/notmuch=
    exits 0. With =Port= in =~/.mbsyncrc= changed to one lab-mail
    does not listen on, it exits non-zero and a FAIL line names the
    mbsync login.

out of scope:
- Moving the list's clients off the jj maildir. lab-process-mail, the
  =mail= bookmark, and Pat's notmuch keep using it until a change of
  their own moves them to lab-mail.
- An archive of the list in git. It is a separate artifact, and can
  be fed from the list's folders like any other client.
- Restricting which jails or local users may post to lab-mail, or
  what they put in From.
- Expunging on either side. A message deleted or moved on one side
  stays in its old folder on the other, marked =\Deleted=, until a
  later change turns on Expunge for that side.
- Mail to and from people outside the list. lab-mail never relays,
  and nobody sends outside mail through it.

alternatives considered: each decision above, what it rejects, and
why.
- A local SMTP server, not a maildir mounted into each client jail. A
  write mount would let an agent rename or delete any message on the
  list. Over SMTP an agent can only add one, and mail protocols are
  used as they are meant to be, not as a file transfer.
- OpenSMTPD, not smtprelay, Postfix, or dma. smtprelay only relays,
  and cannot deliver locally. Postfix can, but it is far larger than
  this job. dma does not listen on the network. OpenSMTPD delivers
  over LMTP natively and matches recipients in a few lines of config.
- Post to lab-mail, not relay to Fastmail. A relay makes a post reach
  the list only by a round trip through Fastmail, and posting fails
  whenever Fastmail does.
- A queuing server, which a relay without a queue was chosen to avoid.
  A queue answers 250 before the next hop has seen the message, so a
  rejection there turns into a bounce nobody sees. Here the only hop
  after the queue is Dovecot in the same jail, which does not refuse
  a well-formed message, and OpenSMTPD refuses a malformed one before
  the queue.
- Deliver only the list address and discard the other known
  addresses, not one copy per recipient, and not refusing every
  address but the list. OpenSMTPD expands each RCPT TO on its own and
  writes one copy per recipient that reaches the maildir, so a reply
  to all would land twice, on lab-mail and on Fastmail. Refusing the
  other addresses would make msmtp abandon every reply to all.
- OpenSMTPD's own header check, not a filter of our own. Its parser
  already refuses a header it cannot read and supplies a missing
  Message-ID. A filter could also refuse a second From or a missing
  Subject, but it would be one more program in every session, and
  neither fault stops the tools that read the list from threading it.
- Check a message in OpenSMTPD's session, not at delivery. A check
  at delivery runs after the client has its 250, so a refused message
  becomes a bounce to an address that is discarded, and the sender
  never learns of it.
- No login to post, unlike IMAP. IMAP needs passwords because its
  logins have different rights. Every poster has the same right, to
  add one message, so a password would tell no two posters apart,
  and every host would hold a secret that guards nothing.
- Reject the whole message on any bad recipient, not deliver to the
  good ones. A bad recipient is most likely a typo, and the sender
  should fix it and send once to everyone.
- mbsync into lab-mail, not a Dovecot imapc proxy to Fastmail. A
  proxy stops serving mail while Fastmail is down.
- Dovecot as the only writer, not mbsync writing the maildir and
  Dovecot reading it. mbsync creates folders 0700 and files 0600
  whatever the umask, so each new message stays out of Dovecot's
  reach until a job widens it, and two writers as two users would
  need a shared group. Dovecot and mbsync would each keep their own
  record of the files, and learn of the other's renames only on the
  next scan. With one writer, Dovecot sees every change as it happens
  and tells IDLE clients at once. The cost is that readers are kept
  read-only by Dovecot's ACL, not by file permissions.
- mbsync logs in to Dovecot over IMAP with a password of its own, not
  through a Tunnel to Dovecot's imap binary. A tunnel needs no
  password, but it runs as the user that runs mbsync, which then needs
  the maildir and the Fastmail credentials both. Every jail on beastie
  can reach 127.0.0.1:2143, so the login that may write the list must
  have a secret.
- =Expunge None= and =Remove None=, not mirroring deletions. Fastmail
  then keeps every message whatever happens on lab-mail, which is the
  safety net for any login that may delete there. Expunge can be
  turned on once the sync has proven itself.
- Name the folders lab-mail syncs, not sync every folder of the
  account. Pat can then make a folder on Fastmail for anything else,
  and it stays out of lab-mail and out of every client.
- inbox needs both INBOX and no answer from the user, not INBOX
  alone. An agent cannot move mail on lab-mail, so its answer is the
  only mark it can leave, and Pat sees at a glance what he has
  answered and not yet filed.
- Archive by folder, not by a tag in one client. A tag is not in the
  list data, so a rebuild of the index loses it and no agent sees it.
  Fastmail's own =Archive= folder is used, not a new one, so archiving
  on Fastmail's web interface means the same. =Next= and =Later= are
  folders for the same reason.
- Import the jj maildir once, not freeze it as an archive. A frozen
  archive would split the list into two places to search, and a reply
  to an old thread would arrive with no parent.
- Passwords only for the logins that may write, not for every login.
  A read-only login can do nothing a password would guard against,
  and agents need no secret.
- A Fastmail account of the list's own, with every message in INBOX,
  not a =lists= folder that a Fastmail rule files into. With nothing
  else arriving in the account, there is nothing to sort, and
  lab-mail serves the folder Fastmail has.
- Dovecot, not Cyrus or Courier. Each of those brings its own mail
  store and admin model, where Dovecot serves a plain maildir and
  takes LMTP.
- IMAP over loopback, not a nullfs-mounted maildir. A mount ties
  every client to beastie's filesystem. A loopback bind is cheap to
  change into an external address later.
- =ip4 = inherit= and a loopback bind, not an address of its own with
  pf rules, or vnet. Nothing needs to restrict which jails on beastie
  use lab-mail, and a jail with its own address cannot reach the
  loopback the other jails share.
- Ports 2525 and 2143, not 25 and 143, so no tool finds lab-mail by
  default and posts or reads mail by accident.
- Logs through syslogd, not each service's own log file. syslogd
  gives one place to look, as for every other FreeBSD service, and
  newsyslog rotates its files by signalling syslogd alone. A service
  that writes its own file must be told to reopen it after rotation,
  and each does that differently.
- A file per service as well as =/var/log/maillog=, not maillog
  alone. maillog interleaves the three services, and the operator
  usually wants to follow one.
- A check script built from base tools, not a monitor such as monit
  or Nagios. A monitor is another daemon to install and configure for
  one jail, and the operator runs the check when it is needed.
- The sync job records its last success in a file, and the check
  reads that file's age, not the sync log. A quiet list writes no log
  lines, so the log cannot tell a stopped sync from a quiet list, and
  a file's age needs no parsing.
