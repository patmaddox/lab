#+TITLE: lab-mail: a mail relay jail for p7x.dev

artifact: a jail instance in this dir, built and operated like the
other instances in =jails/instances=, plus the mail clients that
lab-claude needs to use it.

goal: agents send and read p7x.dev mail without holding the mail
credentials. lab-mail holds them, and it is the only thing that talks
to the mail provider. Agents reach lab-mail over the network (SMTP and
IMAP), never through a shared filesystem, so they need not run on the
same host as lab-mail.

provider: p7x.dev and lists.p7x.dev are hosted on Fastmail.
- IMAP: imap.fastmail.com, port 993, implicit TLS
- SMTP submission: smtp.fastmail.com, port 465, implicit TLS
- lab-mail logs in with the Fastmail account's login and one app
  password, with IMAP and SMTP access. smtprelay and mbsync both use
  them.
- claude@p7x.dev is a sending identity on the Fastmail account.
- The account is the list's own, so mail to the list lands in INBOX.
  No Fastmail rule files it elsewhere.

rights: who may do what to the list.
- Anyone may read the list over IMAP. Any user name logs in with any
  password, and that login may list, fetch, search, and IDLE, and
  nothing else. Dovecot's ACL opens every mailbox read-only for it:
  its attempts to set flags or expunge change nothing, and its
  attempts to append, copy into a mailbox, or move fail.
- IMAP has no anonymous mode, so an agent logs in as its own address,
  such as =claude@p7x.dev=, with any password.
- One login may change the list: =mbsync=. It must give the password
  in =imap-users=, and a wrong one fails. It may set flags, append,
  copy, move, and expunge.
- These rights are enforced by Dovecot's ACL, not by file
  permissions. Dovecot's user can write the whole maildir, so a fault
  in the ACL config would let every login change the list. Steps 7
  and 8 of the acceptance test check the rules.

access:
- lab-mail uses =ip4 = inherit=, like the client jails. A jail with
  its own address has its own 127.0.0.1, which the other jails cannot
  reach.
- smtprelay listens on 127.0.0.1:2525 for SMTP, and Dovecot listens
  on 127.0.0.1:2143 for IMAP. Neither listens on an external address
  or on a standard port (25, 587, 143, or 993), so no tool finds them
  there by default.
- So beastie, and every jail on it that uses =ip4 = inherit=, can use
  lab-mail, and nothing off beastie can. That is the security
  boundary. No pf rules are needed.
- Clients do not authenticate to send. What a client may do to the
  list over IMAP depends on its login (see rights).
- No TLS between clients and smtprelay or Dovecot. The traffic stays
  on loopback.

credentials: the operator stores three files on the host, in
=/jails/data/lab-mail/secrets/=. They never enter the repo.
- =mail-creds= holds the Fastmail login on its first line and the app
  password on its second. Each line is taken whole, so nothing
  depends on where a space falls in it. Only smtprelay and mbsync can
  read it.
- =imap-users= holds the login that may write the list, =mbsync=,
  with a password hash. Only Dovecot's auth process can read it.
- =mbsync-imap= holds the password of mbsync's own Dovecot login.
  Only mbsync can read it.
- The directory is nullfs-mounted read-only into lab-mail, and into
  no other jail.
- smtprelay refuses to start, and the fetch job to run, unless both
  lines of =mail-creds= are present and not empty.
- The instance documents how the operator stores each file.

sending:
- Software: smtprelay (mail/smtprelay).
- smtprelay does not queue. It relays each message to Fastmail SMTP
  during the client's session, logging in with the stored
  credentials, and answers the client's DATA with Fastmail's reply.
  When Fastmail rejects a message, the client gets Fastmail's code
  and text. When Fastmail cannot be reached, the client gets a 4xx
  reply. smtprelay never accepts a message it has not handed to
  Fastmail, and never sends a bounce.
- smtprelay adds one Received header to each message, as every MTA
  does. It does not rewrite the sender, any other header, or the
  body.
- smtprelay checks the envelope sender and each envelope recipient
  against allowlists in its config, before it contacts Fastmail.
  Adding an address is a one-line change to the instance's config.
- Allowed envelope senders (MAIL FROM): =claude@p7x.dev=. Any other
  sender is refused with a 4xx reply.
- Allowed envelope recipients (RCPT TO):
  - =pat@patmaddox.com=
  - any address at =p7x.dev=
  - any address at =lists.p7x.dev=
- Domains match exactly and without regard to case. =p7x.dev= does
  not match its subdomains. That is why =lists.p7x.dev= is listed on
  its own.
- Any other recipient is refused with a 4xx reply to its RCPT TO.
- smtprelay refuses a sender or recipient with 451, and the code is
  not configurable. 4xx means "try again later", which is wrong for
  a refused address, but no client here queues or retries, so the
  refusal still ends the send.
- A message with any refused recipient is sent to no one. smtprelay
  refuses the recipient; the client then abandons the message (see
  clients).

reading:
- Software: isync (mail/isync) for mbsync, and Dovecot (mail/dovecot)
  for IMAP.
- Dovecot is the only program that writes the list. Every change to
  it, such as a fetch from Fastmail, goes through Dovecot, as
  Dovecot's user.
- mbsync in lab-mail pulls new messages from Fastmail's INBOX into
  Dovecot's once a minute, as an IMAP client of each. It logs in to
  Dovecot on 127.0.0.1:2143 as =mbsync=, with the password in
  =mbsync-imap=. It never opens the maildir.
- The jail's cron(8) runs the fetch job from a file in =/etc/cron.d=,
  as mbsync's user, so it is not in any user's crontab. A run that
  starts while the previous one is still going exits at once.
- The fetch job records the time of its last successful pull, so a
  check can tell a fetch that stopped from a list that is quiet.
- mbsync only pulls new messages. It never sends new messages, flag
  changes, or deletions to Fastmail, and it never removes a message
  from lab-mail. A message deleted from INBOX on Fastmail, or moved
  out of it, stays on lab-mail.
- The maildir lives in =/jails/data/lab-mail/mail/=, mounted
  read-write into lab-mail only, so a rebuild of the jail keeps the
  list. Dovecot's user owns it.
- The operator creates that directory and its subdirectories on the
  host before the jail starts, as with the credentials. The jail does
  not create anything on the host.
- Dovecot serves the maildir as INBOX, as on Fastmail. INBOX is a
  folder of the maildir. Every login sees the same mailbox, and
  Dovecot's ACL gives each login the rights in the rights section.
- Dovecot serves IMAP only. It does not run POP3, LMTP, or
  submission.
- Reading keeps working from lab-mail's copy while Fastmail is down.

logs:
- Every service in lab-mail logs through syslogd(8) in the jail:
  smtprelay, the fetch job, and Dovecot. Each has a file of its own
  under =/var/log/lab-mail/=: =smtprelay.log=, =fetch.log=, and
  =dovecot.log=. They also land together in =/var/log/maillog=, as
  all mail logs do by default.
- smtprelay logs each session: the client, the envelope, and
  Fastmail's reply. The fetch job logs each run that brings new
  messages, with mbsync's counts, and every failure. Dovecot logs each
  login and every error.
- newsyslog(8) rotates the files daily and keeps a week, as it does
  =/var/log/maillog=.
- syslogd in lab-mail opens no network socket. The jail shares
  beastie's addresses, so a socket would contend for UDP port 514
  with every other jail's syslogd, and nothing sends lab-mail logs
  over the network.

check:
- =just check=, run on beastie in the instance's directory, checks
  that lab-mail is set up and running. It exits 0 only if every check
  passes. It prints one line per check, saying ok or FAIL and what it
  checked, so the operator sees what is wrong.
- It checks that:
  - the jail is running;
  - =mail-creds= is present, neither of its lines is empty, and
    smtprelay and mbsync can read it while Dovecot's user cannot;
  - =imap-users= has an entry for =mbsync=, and =mbsync-imap= is not
    empty;
  - each of those two is readable by its reader and by no other
    service user;
  - the mail state directories exist with the owners the README
    gives;
  - syslogd, cron, smtprelay, and Dovecot are running;
  - smtprelay accepts connections on 127.0.0.1:2525, and Dovecot on
    127.0.0.1:2143;
  - the last successful fetch was within the last five minutes;
  - each log file exists.
- The check only reads. It changes nothing in the jail and sends no
  mail, so it is safe to run at any time.

clients: lab-claude.
- Packages: mail/isync and mail/msmtp, added to the existing
  mail/notmuch.
- msmtp sends through 127.0.0.1:2525 as claude@p7x.dev. When the
  server refuses any recipient, msmtp sends no message and exits
  non-zero with the server's reply, so the whole message is
  abandoned.
- mbsync pulls INBOX from 127.0.0.1:2143 into a maildir in the
  agent's home, and =notmuch new= indexes it there. The agent searches
  and reads the local index, not IMAP.
- lab-claude documents the commands to fetch and to send.

acceptance test: run from lab-claude, except where a step says
beastie.
1. pat@patmaddox.com sends a message to lab@lists.p7x.dev.
2. Within two minutes, mbsync fetches the message from lab-mail and
   =notmuch search= finds it.
3. The agent replies with msmtp as claude@p7x.dev to pat@patmaddox.com
   and lab@lists.p7x.dev. msmtp exits 0.
4. pat@patmaddox.com receives the reply.
5. A message to pat@patmaddox.com and someone@example.com is refused
   at RCPT TO for someone@example.com. msmtp exits non-zero and
   pat@patmaddox.com receives nothing.
6. A message from someone@p7x.dev is refused. msmtp exits non-zero.
7. Logged in as =claude@p7x.dev=, an IMAP STORE of =\Deleted=
   followed by EXPUNGE on INBOX changes nothing, and an APPEND to
   INBOX fails. The message stays in place, its flags unchanged, in
   lab-mail's maildir and on Fastmail.
8. A login as =mbsync= with a wrong password fails.
9. On beastie, =just check= exits 0.
10. On beastie, with smtprelay stopped, =just check= exits non-zero
    and a FAIL line names smtprelay.

out of scope:
- The lab-devel list and the process-email workflow. They keep using
  the maildir in jj.
- An archive of the list in git. It is a separate artifact, and can
  be fed from INBOX like any other client.
- Restricting which jails or local users may use lab-mail.
- Delivery failures that happen after Fastmail has accepted a
  message, and where Fastmail delivers mail for claude@p7x.dev.

alternatives considered: each decision above, what it rejects, and
why.
- Relay without a queue, not a queuing MTA (OpenSMTPD, Postfix). A
  queue answers 250 before Fastmail sees the message, so a rejection
  comes back later as a bounce the sender may never see. The relay
  keeps every failure in the client's session. The cost is that
  nothing holds mail while Fastmail is unreachable; the client gets a
  4xx reply and must send again.
- No queue in the client either (msmtpq). A client queue also answers
  "sent" before Fastmail has the message, which moves the same problem
  one hop closer to the sender instead of removing it. An agent can
  act on msmtp's non-zero exit, but a message waiting in a queue is a
  state nothing checks. Outages are rare and short, and a failed send
  in Emacs keeps the compose buffer, so the message is not lost.
- smtprelay, not other relays. Postfix's smtpd_proxy_filter hands mail
  to a local filter, which cannot log in to Fastmail. Sendmail's m4
  config costs effort for no gain. dma and msmtp do not listen on the
  network, so each client jail would need the credentials. Dovecot
  submission needs clients to log in, and has no recipient allowlist.
- Refuse an address with smtprelay's 451, not a 5xx from a locally
  patched smtprelay or from another relay. A local patch means
  building smtprelay from ports and keeping the patch current, and no
  other relay weighed here has both a recipient allowlist and
  pass-through of Fastmail's reply. The client exits non-zero either
  way.
- Check the sender against an allowlist, and never rewrite it. An
  unchecked sender fails only at Fastmail, if at all; rewriting would
  send mail as someone the client did not ask for.
- Reject the whole message on any bad recipient, not deliver to the
  good ones. A bad recipient is most likely a typo, and the sender
  should fix it and send once to everyone.
- mbsync into lab-mail, not a Dovecot imapc proxy to Fastmail. A
  proxy stops serving mail while Fastmail is down.
- Dovecot as the only writer, not mbsync writing the maildir and
  Dovecot reading it. mbsync creates folders 0700 and files 0600
  whatever the umask, so each new message stays out of Dovecot's
  reach until a job widens it, and two writers as two users would
  need a shared group. Dovecot and mbsync would each keep their own
  record of the files, and learn of the other's renames only on the
  next scan. With one writer, Dovecot sees every change as it happens
  and tells IDLE clients at once. The cost is that readers are kept
  read-only by Dovecot's ACL, not by file permissions.
- mbsync logs in to Dovecot over IMAP with a password of its own, not
  through a Tunnel to Dovecot's imap binary. A tunnel needs no
  password, but it runs as the user that runs mbsync, which then needs
  the maildir and the Fastmail credentials both. Every jail on beastie
  can reach 127.0.0.1:2143, so the login that may write the list must
  have a secret.
- Passwords only for the logins that may write, not for every login.
  A read-only login can do nothing a password would guard against,
  and agents need no secret.
- A Fastmail account of the list's own, with every message in INBOX,
  not a =lists= folder that a Fastmail rule files into. With nothing
  else arriving in the account, there is nothing to sort, and
  lab-mail serves the folder Fastmail has.
- Dovecot, not Cyrus or Courier. Each of those brings its own mail
  store and admin model, where Dovecot serves a plain maildir.
- IMAP over loopback, not a nullfs-mounted maildir. A mount ties
  every client to beastie's filesystem. A loopback bind is cheap to
  change into an external address later.
- =ip4 = inherit= and a loopback bind, not an address of its own with
  pf rules, or vnet. Nothing needs to restrict which jails on beastie
  use lab-mail, and a jail with its own address cannot reach the
  loopback the other jails share.
- Ports 2525 and 2143, not 25 and 143, so no tool finds lab-mail by
  default and sends or reads mail by accident.
- The login and app password in one =mail-creds= file, not the login in
  the repo config and the password in a file of its own. The login is
  not secret, but keeping both together gives the operator one file
  to manage, which smtprelay and mbsync read the same way.
- One app password, not one for SMTP and one for IMAP. Both live in
  the same jail behind the same mount, so two add no protection.
- Logs through syslogd, not each service's own log file (Dovecot's
  log_path, smtprelay's log_file). syslogd gives one place to look,
  as for every other FreeBSD service, and newsyslog rotates its files
  by signalling syslogd alone. A service that writes its own file
  must be told to reopen it after rotation, and each does that
  differently.
- A file per service as well as =/var/log/maillog=, not maillog
  alone. maillog interleaves the three services, and the operator
  usually wants to follow one.
- A check script built from base tools, not a monitor such as monit
  or Nagios. A monitor is another daemon to install and configure for
  one jail, and the operator runs the check when it is needed.
- The fetch job records its last success in a file, and the check
  reads that file's age, not the fetch log. A quiet list writes no
  log lines, so the log cannot tell a stopped fetch from a quiet
  list, and a file's age needs no parsing.
- Pat's own mail client is not part of this spec. With no queue,
  there is nothing about it for lab-mail to provide. Sending as
  pat@patmaddox.com takes one more allowed sender and an msmtp entry
  in his client.
